## 一、先搞懂一个比喻

### 你的项目是个"餐厅后厨"

| 厨房角色 | 项目对应 | 做什么 |
|---|---|---|
| 顾客点单 | 用户上传 Excel | "我要报 10 个断路器的价" |

**Agent 的本质就是这个厨师长** —— 它自己决定"下一步该谁干活"，而不是你硬编码死板的顺序。

### 📘 文件 1：`models.py` — 数据契约

#### 通俗理解

**这是什么？** 这个文件定义了项目里所有"数据结构"长什么样。

**为什么要它有？** 想象你要填表格——你得先看表头有哪些列，对吧？程序也一样。在往数据库写数据、从 API 返回 JSON、或者 Agent 各节点之间传递信息之前，必须先把数据的形状定好。**这就是"契约"的含义：所有人遵守同一套模板。**

**面试怎么说？**
> "我用 Pydantic BaseModel 做数据契约。好处有三：①运行时类型校验，脏数据进不来；②自动生成 JSON Schema，FastAPI 能直接用；③ IDE 有完整提示，重构安全。这是 Agent 工程化的基础——状态、工具入参出参、API 请求响应全部统一模型，避免字典满天飞。"

#### 逐行拆解

```python
from pydantic import BaseModel, Field
from typing import List, Optional
from enum import Enum
```

- `BaseModel`：Pydantic 的基类，让你的类自动拥有"字段校验 + JSON 序列化"能力
- `Field`：给字段加约束，比如 `ge=1` 表示"大于等于 1"
- `Enum`：枚举类型，限定取值只能是预设的几个选项

```python
class ProductCategory(str, Enum):
    COMPONENT = "元器件"
    CABINET = "柜体"
    AUXILIARY = "辅材"
    UNKNOWN = "未知"
```

**解释**：产品分类只能选这四个，不能随便填"电器""设备"之类的——这就是枚举的价值，**防止脏数据**。

```python
class Product(BaseModel):
    name: str = Field(description="产品名称")
    model: Optional[str] = Field(default=None, description="型号")
    spec: Optional[str] = Field(default=None, description="规格参数")
    brand: Optional[str] = Field(default=None, description="品牌")
    category: ProductCategory = Field(default=ProductCategory.UNKNOWN, description="产品类别")
    quantity: int = Field(default=1, ge=1, description="数量")
    unit: Optional[str] = Field(default="个", description="单位")
```

**关键语法**：
- `Optional[str]`：可以是字符串，也可以是 `None`（表示可选字段）
- `int`：必须是整数
- `ge=1`：大于等于 1（如果用户传 `quantity=0`，Pydantic 会直接报错）
- `description=`：给字段写说明，这在 AI 看到数据时特别有用（AI 会读 description 来理解字段含义）

```python
class PriceRecord(BaseModel):
    product_name: str
    model: Optional[str]
    source: str          # "本地样本" 或 "震坤行"
    price: float = Field(ge=0)  # 价格不能为负数
    confidence: float = Field(default=0.5, ge=0, le=1)  # 置信度 0~1
    fetched_at: Optional[str] = None  # 获取时间（ISO 格式）
```

**解释**：这是"价格记录"的结构。注意 `source` 字段——它会告诉你价格是从哪来的（本地库还是网页），这在调试时很有用。

```python
class QuotationStatus(str, Enum):
    PENDING = "待处理"
    PARSING = "解析中"
    PRICING = "查价中"
    VALIDATING = "价格核查中"
    CALCULATING = "计算中"
    HUMAN_REVIEW = "人工确认"
    DONE = "完成"
    ERROR = "错误"
```

**关键**：这个枚举就是 Agent 的"状态机"。Agent 每走一步就改一次 `status`，你通过查 `status` 就知道当前走到哪了。

```python
class QuotationItem(BaseModel):
    product: Product              # 产品信息
    cost_price: Optional[float] = None  # 成本价（查不到的话就是 None）
    profit_rate: float = 0.15     # 利润率（默认 15%）
    discount: float = 1.0         # 折扣系数（默认不打折）
    unit_price: float = 0.0       # 单价
    total_price: float = 0.0      # 总价
    remark: str = ""              # 备注（可以写警告信息）
    price_source: Optional[str] = None    # 价格来源
    validation_warning: Optional[str] = None  # 核查警告
```

**解释**：这是最终报价行的结构。注意 `cost_price` 是 `Optional[float]`——查不到价的时候它就是 `None`，这时候就需要人工确认。

#### 面试速答卡

> **Q：为什么不用字典（dict），非要用 Pydantic 模型？**
>
> **答**：三个原因。①类型安全：字典可以乱塞键值对，Pydantic 会在入口处拦截不符合结构的数据；②IDE 友好：`item.product.name` 有自动补全，`dict["product"]["name"]` 全靠脑内维护；③序列化方便：Pydantic 的 `.model_dump()` 一键转字典，`.model_dump_json()` 一键转 JSON，FastAPI 自动调用。Agent 场景下还有额外好处——LLM 能看到模型的 `description`，帮助它理解字段的业务含义。

### 📘 文件 2：`agent.py` — Agent 核心 ⭐⭐⭐

**这是整个项目最重要的文件，面试必问。**

#### 通俗理解

**什么是 Agent？** Agent 就是一个"会拐弯的流程"。普通脚本是一条直线走到底（步骤 A→B→C→D），Agent 走到岔路口会根据情况选路（如果有缺失 → 去等人，没缺失 → 直接算）。

**为什么叫 LangGraph？** LangGraph 是一个专门做"状态机"的库。它的核心理念很简单：
- **State**（状态）：全局共享的记事本，所有节点共读共写
- **Node**（节点）：干活的函数，每个函数就是一个工位
- **Edge**（边）：箭头，决定从哪个节点走到哪个节点

#### 逐段拆解

```python
class GraphState(TypedDict):
    task_id: str
    customer_name: str
    profit_rate: float
    products: List[Product]
    items: List[QuotationItem]
    status: str
    messages: List[str]
    pending_products: List[Product]      # 没查到价的产品
    manual_prices: Dict[str, float]      # 人工输入的价格 {产品名：价格}
    validation_results: Dict[str, PriceValidationResult]  # 核查结果
```

**重点**：这就是"全局记事本"。每个节点进来都能看到这本笔记，修改后带出去给下一个节点。

关键字段：
- `products`：从 Excel 解析出来的原始产品列表
- `items`：已经算完价的报价行
- `pending_products`：查不到价、需要人工干预的产品
- `manual_prices`：人工补充的价格（比如 {"电缆": 8.5, "按钮开关": 12.0}）
- `messages`：每一步的操作日志（方便调试和展示）
- `validation_results`：价格核查的结果

```python
def init_state(products: List[Product], customer_name: str = "", profit_rate: float = 0.15) -> GraphState:
    return {
        "task_id": str(uuid.uuid4())[:8],  # 任务 ID，前 8 位
        "customer_name": customer_name,
        "profit_rate": profit_rate,
        "products": products,
        "items": [],              # 初始为空，后面逐渐填充
        "status": QuotationStatus.PENDING.value,
        "messages": ["开始报价流程"],
        "pending_products": [],
        "manual_prices": {},
        "validation_results": {},
    }
```

**解释**：这是创建"第一页空白笔记"的函数。每次用户上传一个新 Excel，就调用一次。

```python
def parse_step(state: GraphState) -> GraphState:
    state["status"] = QuotationStatus.PARSING.value
    state["messages"].append(f"已解析 {len(state['products'])} 个产品")
    return state
```

**规律**：每个节点函数都是同一个模式 —— **收 State → 改 State → 回 State**。就这么简单。

#### 节点流程图（文字版）

```
入口 ──→ [parse] ──→ [price_lookup] ──→ [validate_prices] ──┬──→ (判断)
                                                             │
                                ┌──────────────┐             ├─→ human_review ──→ END
                                │  有缺失？     │             │
                                └──────────────┘             │
                                否 ──→ [calculate] ──────────┘
```

#### 四个核心节点详解

##### 节点 1：`parse_step`（解析）

```python
def parse_step(state: GraphState) -> GraphState:
    state["status"] = QuotationStatus.PARSING.value
    state["messages"].append(f"已解析 {len(state['products'])} 个产品")
    return state
```

**做了什么**：标记状态为"解析中"，记一条日志。实际解析工作由 `parser.py` 在外部完成，这里只是更新状态。

**面试表达**："解析本身是确定性操作，不需要 LLM 参与，所以它只是一个简单的 Node，不是复杂的 Tool Calling。"

##### 节点 2：`price_lookup_step`（查价）

```python
def price_lookup_step(state: GraphState) -> GraphState:
    state["status"] = QuotationStatus.PRICING.value
    items = []
    pending = []
    for p in state["products"]:
        record = search_local_price_tool(p)      # 先查本地库
        if not record:
            record = search_web_price_tool(p)     # 本地没有才上网
        if record:
            item = calculate_item_price(p, record.price, state["profit_rate"])
        else:
            item = calculate_item_price(p, None, state["profit_rate"])
            pending.append(p)                     # 没查到价，放入待确认
        items.append(item)
    state["items"] = items
    state["pending_products"] = pending
    save_task_state(state)                        # 保存到内存
    return state
```

**关键点**：
1. **优先级策略**：先查本地库 → 没有才上网。这是为了减少网络请求、提高效率。
2. `pending` 列表：收集所有查不到价的产品，后续用于"判断是否要暂停"。
3. `save_task_state(state)`：把状态存到内存字典 `_task_states`，这样即使服务重启也能恢复（虽然目前只支持单机 MVP）。

**面试表达**："查价遵循'本地优先、网络兜底'策略。本地库查询用 LIKE 模糊匹配，O(n) 复杂度。如果产品量大应该加数据库索引。"

##### 节点 3：`validate_prices_step`（价格核查）

```python
def validate_prices_step(state: GraphState) -> GraphState:
    state["status"] = QuotationStatus.VALIDATING.value
    validation_results = {}
    warnings = []

    for item in state["items"]:
        if item.cost_price is not None:  # 只核查有价格的产品
            result = validate_price_tool(item.product, item.cost_price)
            validation_results[item.product.name] = result

            if result.warning:
                warnings.append(f"{item.product.name}: {result.warning}")
                item.remark = f"{item.remark}; {result.warning}".strip("; ")

    state["validation_results"] = validation_results

    if warnings:
        state["messages"].append(f"价格核查发现 {len(warnings)} 个警告")
    else:
        state["messages"].append("价格核查通过")

    save_task_state(state)
    return state
```

**做了什么**：充当"质检员"角色，检查所有查到的价格是否合理。不合理的价格不会阻止流程（不会抛异常），但会打上警告标签。

**面试表达**："价格核查是确定性流程，不依赖 LLM。我们实现了两层核查：基础检查（价格为正、在合理区间）和历史对比（偏离历史均价 30% 以上报警）。这是 Agent 可靠性的基础——让规则兜底，让 AI 决策。"

##### 节点 4：`human_review_decision`（判断路由）

```python
def human_review_decision(state: GraphState) -> str:
    if state["pending_products"] and not state.get("manual_prices"):
        return "human_review"      # 有缺失且无人工确认 → 去等人
    return "calculate"             # 否则 → 直接算
```

**这就是"Agent 会拐弯"的物理实现**。返回一个字符串，LangGraph 根据字符串决定走哪条路。

**面试表达**："条件边（Conditional Edge）用一个路由函数决定下一步去哪。这个函数只返回一个字符串，LangGraph 负责映射到对应的 Node。这种设计比硬编码 if-else 灵活得多——新增分支只需加映射，不用改主逻辑。"

##### 节点 5：`calculate_step`（计算）

```python
def calculate_step(state: GraphState) -> GraphState:
    state["status"] = QuotationStatus.CALCULATING.value

    # 如果有人工输入的价格，应用它们
    if state.get("manual_prices"):
        for item in state["items"]:
            if item.product.name in state["manual_prices"]:
                manual_price = state["manual_prices"][item.product.name]
                new_item = calculate_item_price(item.product, manual_price, state["profit_rate"])
                item.cost_price = new_item.cost_price
                item.unit_price = new_item.unit_price
                item.total_price = new_item.total_price
                item.remark = "人工确认价格"

    total = sum(i.total_price for i in state["items"])
    state["status"] = QuotationStatus.DONE.value
    state["messages"].append(f"报价计算完成，总价: {total:.2f}")
    save_task_state(state)
    return state
```

**解释**：把成本 × 利润率 → 得到报价单价 → 乘以数量 → 得到总价。

#### 组装图（build_agent）

```python
def build_agent():
    workflow = StateGraph(GraphState)

    # 1. 注册节点
    workflow.add_node("parse", parse_step)
    workflow.add_node("price_lookup", price_lookup_step)
    workflow.add_node("validate_prices", validate_prices_step)
    workflow.add_node("calculate", calculate_step)
    workflow.add_node("human_review", human_review_step)

    # 2. 设置入口
    workflow.set_entry_point("parse")

    # 3. 添加无条件边
    workflow.add_edge("parse", "price_lookup")
    workflow.add_edge("price_lookup", "validate_prices")

    # 4. 添加条件边（会拐弯的地方）
    workflow.add_conditional_edges("validate_prices", human_review_decision, {
        "human_review": "human_review",
        "calculate": "calculate",
    })

    # 5. 添加终点的边
    workflow.add_edge("human_review", END)
    workflow.add_edge("calculate", END)

    return workflow.compile()
```

**记忆**：注册节点 → 设入口 → 加固定边 → 加条件边 → 编译。五步搞定。

#### 运行流程（run_quotation_agent）

```python
def run_quotation_agent(products: List[Product], customer_name: str = "", profit_rate: float = 0.15) -> GraphState:
    agent = build_agent()                       # 编译图
    state = init_state(products, customer_name, profit_rate)  # 初始化状态
    result = agent.invoke(state)                # 执行！
    return result
```

**极简**：三步跑完全流程。编译 → 初始化 → 执行。

#### 面试高频追问

> **Q1：Agent 和普通 Workflow 有什么区别？**
>
> **答（按当前代码）**：报价主链由 `app/agent.py::build_agent()` 预先定义节点和分支，是确定性 Workflow；价格查询、人工暂停和计算都不由模型选择。独立问答分支的 `app/assistant.py` 允许模型在四个只读工具中选择，属于局部 Agent 能力。准确表述是“确定性报价工作流 + 受控只读 AI 助手”。

> **Q2：State 在节点之间怎么传递？**
>
> **答**：用 TypedDict 定义一份共享状态，每个节点接收它、修改它、再返回它，LangGraph 负责传给下一个节点。进阶点是：如果多个节点并发写同一个字段，需要给字段加 Annotated[List, operator.add] 声明合并规则（reducer），否则会互相覆盖。我的项目目前是串行执行，还没用到，但这是上线必补的一课。

> **Q3：当前状态的持久化方案有什么缺陷？**
>
> **答（按当前代码）**：`app/agent.py::TaskSnapshot` 和 `app/db.py` 已将任务状态写入 SQLite，可在进程重启后按任务 ID 恢复；保存时用版本比较拦截旧状态覆盖。当前没有 LangGraph 内置 checkpointer，也未验证多人并发、备份恢复或跨实例部署。是否改用其他持久化方案须由这些需求和测试决定。

### 📘 文件 3：`tools.py` — Agent 的工具箱

#### 通俗理解

**Agent 怎么"用工具"？** 工具就是 Agent 能干的事的接口。你可以把它理解为 Agent 的技能包。

**面试表达**："Tool Calling 是 Agent 的核心能力。我们把每个外部操作封装成独立函数，签名清晰、职责单一。LangGraph 里工具可以是普通 Python 函数，不需要特殊装饰器——这和 LangChain 的 @tool 不同，更轻量。工具的返回值应该是结构化数据（PriceRecord、QuotationItem），不是字符串，这样下游节点可以直接消费。"

#### 逐函数解读

```python
def search_local_price_tool(product: Product) -> PriceRecord:
    """查询本地价格库"""
    records = search_local_price(product.name, product.model)
    if records:
        return records[0]
    return None
```

**做了什么**：调用 `db.py` 的查询功能，返回最匹配的一条价格记录。如果没有就返回 `None`。

```python
def search_web_price_tool(product: Product) -> PriceRecord:
    """外部网站查价（接入 Playwright）"""
    try:
        from .web_scraper import search_web_price_sync
        return search_web_price_sync(product)
    except Exception as e:
        from .config import logger
        logger.warning(f"网页查价失败: {e}")
        return None
```

**解释**：可能失败的网络请求用 try-except 包裹，失败了记日志并返回 None，不影响整体流程。

```python
def validate_price_tool(product: Product, price: float) -> PriceValidationResult:
    """价格核查工具：检查价格是否合理"""
    from .validator import validate_price
    return validate_price(product, price)
```

**关键点**：把这个"质检"功能也包装成工具，Agent 可以随时调用它。体现了"单一职责"原则——查价归查价，核查归核查。

### 📘 文件 4：`parser.py` — Excel 解析器

#### 通俗理解

用户上传的 Excel 列名可能五花八门——"产品名称"/"名称"/"product"——这个模块把它们统一翻译成标准字段。

**面试表达**："解析器做了两件事：①列名归一化，用映射表把各种写法统一到标准字段；②分类推断，根据产品名称关键词自动判断是元器件、柜体还是辅材。这两步都是确定性规则，不依赖 LLM——因为电气产品的命名是有规律的，用规则比用模型更快、更准、更便宜。"

#### 关键函数

```python
def normalize_column_name(col: str) -> str:
    col = str(col).strip().lower()
    mapping = {
        "产品名称": "name",
        "名称": "name",
        "产品": "name",
        "product": "name",
        "型号": "model",
        # ...更多映射
    }
    return mapping.get(col, col)
```

**技巧**：`mapping.get(col, col)` 的意思是——如果能找到映射就用映射值，找不到就用原值。这样即使遇到没见过的列名也不会报错。

```python
def infer_category(name: str) -> ProductCategory:
    name = name.lower()
    if any(k in name for k in ["柜", "箱", "屏"]):
        return ProductCategory.CABINET
    elif any(k in name for k in ["线", "排", "辅料", "胶带", "螺丝"]):
        return ProductCategory.AUXILIARY
    elif any(k in name for k in ["断路器", "接触器", "继电器", "开关", "按钮"]):
        return ProductCategory.COMPONENT
    return ProductCategory.UNKNOWN
```

**逻辑**：关键词匹配。只要名字里包含"柜"就认为是柜体，包含"断路器"就认为是元器件。简单粗暴但有效。

### 📘 文件 5：`main.py` — FastAPI 入口

#### 通俗理解

这是"对外暴露的窗口"。用户不直接接触 agent.py 或 parser.py，而是通过 HTTP API 跟项目交互。

**面试表达**："FastAPI 提供 RESTful API，支持文件上传、异步处理、自动文档生成。我们用 /upload 触发 Agent，/tasks/{id}/confirm 做人工确认，/export 导出报价单。CORS 中间件允许前端跨域访问。生产环境应该加认证、限流、请求日志。"

#### 端点详解

| 端点 | 方法 | 作用 | 入参 | 出参 |
|---|---|---|---|---|
| `/` | GET | 健康检查 | 无 | `{"message": "电气报价 Agent"}` |
| `/upload` | POST | 上传 Excel 触发报价 | multipart/form-data（文件+客户名+利润率） | `{task_id, status, items, messages, pending_count}` |
| `/tasks/{task_id}` | GET | 查询任务状态 | 路径参数 task_id | `{task_id, status, items, messages}` |
| `/tasks/{task_id}/confirm` | POST | 人工确认缺失价格 | `{"产品名": 价格}` | `{task_id, status, items, messages}` |
| `/export` | POST | 导出报价 Excel | `{items: [...], customer_name: "xxx"}` | 文件下载 |

#### 关键代码

```python
@app.post("/upload")
```

**流程**：接收文件 → 保存 → 解析 → 跑 Agent → 打包返回。一气呵成。

#### 面试表达

> **Q：为什么用 async def？**
>
> **答**：FastAPI 的 async 意味着非阻塞。上传大文件时如果用同步函数，服务器会卡住等文件传完才能响应其他请求。async 让 I/O 操作（文件读写、数据库查询、HTTP 请求）可以在后台进行，前台继续处理新请求。但要注意——async 不适合 CPU 密集型任务，比如大量的数值计算。我们的 Agent 流程里有少量 CPU 密集操作（遍历产品列表、乘法计算），但整体以 I/O 为主，所以用 async 是合理的。

### 📘 文件 6：`pricing.py` — 报价计算规则

#### 通俗理解

成本 × (1 + 利润率) × 折扣 = 单价。就这么简单。但这个简单函数是整个业务的价值核心。

**面试表达**："报价规则是纯函数，输入产品和成本价，输出报价项。没有副作用，容易测试。真实业务里规则会更复杂（阶梯定价、客户等级折扣、运费分摊），但架构一样——把规则从 Agent 流程里抽出来，单独维护、单独测试。"

```python
def calculate_item_price(product: Product, cost_price: float, profit_rate: float = 0.15, discount: float = 1.0) -> QuotationItem:
    if cost_price is None:
        return QuotationItem(product=product, cost_price=None, unit_price=0.0, total_price=0.0, remark="价格未查到")

    unit_price = round(cost_price * (1 + profit_rate) * discount, 2)
    total_price = round(unit_price * product.quantity, 2)

    return QuotationItem(
        product=product,
        cost_price=cost_price,
        profit_rate=profit_rate,
        discount=discount,
        unit_price=unit_price,
        total_price=total_price,
        remark="",
    )
```

**关键点**：
- `round(..., 2)`：保留两位小数，财务精度
- `if cost_price is None`：查不到价时返回空报价项，不抛异常

### 📘 文件 7：`validator.py` — 价格核查

#### 通俗理解

查到的价格不能直接用——可能是错的（过期、单位错、规格不匹配）。这个模块当"质检员"，检查价格是否合理。

**面试表达**："价格核查是确定性流程的关键一环。我们实现了两层核查：①基础核查——价格为正、在合理区间内；②历史核查——新价格和历史均价偏离超过 30% 就标记警告。这不是 AI 决策，是硬编码的业务规则。Agent 的可靠性恰恰来自这些'不智能'的兜底逻辑。"

```python
PRICE_RANGES = {
    "断路器": (10, 500),    # 正常 10~500 元
    "接触器": (20, 800),    # 正常 20~800 元
    "配电箱": (50, 2000),   # 正常 50~2000 元
    # ...更多范围
}
DEVIATION_THRESHOLD = 0.3  # 30%
```

**逻辑**：
1. 基础检查：价格是否为正数
2. 范围检查：是否在预期区间内（如断路器不在 10~500 元之间则报警）
3. 历史对比：如果历史有相同产品价格，新价格偏离 > 30% 则报警

### 📘 文件 8：`retry.py` — 重试机制

#### 通俗理解

网络请求可能失败（超时、反爬），失败了就等一会儿再试，最多试 3 次。

**面试表达**："重试是分布式系统的基本功。我们实现了指数退避策略：第一次等 1 秒，第二次等 2 秒，第三次等 4 秒。还加了兜底值模式——查价失败不抛异常，返回 None 让人工确认环节兜住。这保证了 Agent 流程不会因为单个产品的查价失败而中断。"

```python
@retry_with_fallback(fallback_value=None, max_retries=3, delay=1.0, backoff=2.0)

    # 可能失败的网络请求
    pass
```

**参数解读**：
- `fallback_value=None`：全部重试失败后的返回值（不抛异常）
- `max_retries=3`：最多重试 3 次
- `delay=1.0`：第一次重试等 1 秒
- `backoff=2.0`：每次重试间隔翻倍（1s → 2s → 4s）

## 四、面试冲刺包

### 必背知识卡片

#### 卡片 1：Agent 是什么

> Agent = 状态机 + 工具调用 + 人类在环。
> 普通脚本是"开发者预定义流程"，Agent 是"运行时根据数据决定流程"。
> 判断标准：如果分支条件全是 if/else 硬编码，它是 Workflow。如果分支条件是 LLM 在运行时决定的，它是真正的 Agent。
> 本项目是"确定性骨架 + 局部自主"的混合形态，原因是报价场景对可控性要求极高，纯自主 Agent 不可接受。

#### 卡片 2：LangGraph 的优势

> ①可中断可恢复——配合 checkpointer 能做真正的人工确认；②状态显式化——State、Node、Edge 三件套把流程画成一张图，可读可测；③可观测——能回放执行轨迹排障。

#### 卡片 3：为什么用 Pydantic

> ①运行时类型校验；②自动生成 JSON Schema；③IDE 有完整提示；④LLM 能看到字段 description。Agent 场景下第 4 点特别重要——模型依赖描述理解业务含义。

#### 卡片 4：当前局限与改进

> ①状态存储用内存字典，生产换 LangGraph checkpointer；②查价用 LIKE 模糊匹配，量大需加索引；③查价逻辑是串行，生产可用 asyncio.gather 并发；④没有 LLM 参数抽取，无法处理"正泰32A两匹"→DZ47-63/2P C32 的非结构化输入。

## 五、常见面试题

| Agent 和 Workflow 区别？ | 控制权归属。Workflow 预定义，Agent 运行时决定。我们是混合形态。 |
