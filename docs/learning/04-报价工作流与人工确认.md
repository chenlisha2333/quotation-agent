# 报价工作流与人工确认

更新日期：2026-10-21。先读 [人民币与施耐德产品匹配](07-人民币与施耐德产品匹配.md)；本篇重点理解工作流怎样暂停以及人工价格怎样继续计算。

## 业务目标、核心技术与选择理由

报价需依次解析、核对产品和价格、检查异常、计算。缺少合格价格时应暂停，让人补充；品牌或型号有问题时须修正清单。`app/agent.py` 用 LangGraph 把固定步骤和条件分支写清楚，用 `TypedDict` 描述共享状态；在数据库查价和历史核查都成功后，才把任务状态首次存入 SQLite。这是确定性工作流，**不是**大模型自主选择工具的 Agent。持久化详见[模块 4](08-任务持久化与操作审计.md)，角色审批详见[模块 5](09-角色审批与客户报价.md)。

**简单解释**：状态是一张“这次报价做到哪一步”的记录。**专业定义**：`GraphState` 是 LangGraph 节点共享的 `TypedDict` 状态契约；节点接收状态、返回更新，条件边选择下一节点。

## 文件、函数与数据流

`app/main.py::upload_excel → app/agent.py::run_quotation_agent → build_agent → parse_step → price_lookup_step → validate_prices_step → human_review_decision`。没有待处理行时进入 `calculate_step`；有待处理行时进入 `human_review_step` 并结束本次图执行。随后 `/tasks/{task_id}/confirm` 调用 `apply_manual_prices`；它校验全部明细 ID 和价格后直接调用 `calculate_step`。`app/product_policy.py` 控制品牌与价格准入，`app/pricing.py` 负责金额计算。

## 核心代码逐段解释

1. `init_state` 为一次任务生成 UUID，为每行产品分配 `line-1`、`line-2` 等 `item_id`，并把品牌别名归一成“施耐德”。状态中固定 `currency="CNY"`，还有 `pending_products` 和以明细 ID 为键的 `review_reasons`。
2. `price_lookup_step` 先用 `product_issue` 检查品牌、型号，再通过 `search_local_price_tool` 找已核准的人民币价格，并用 `eligible_price` 再核验一次。合格价格进入 `calculate_item_price`；不合格的行写明原因并进入待处理列表。数据库读取/解码失败会抛出 `db.PriceLookupError`，不会生成“待人工补价”状态。网页抓价实验模块不在此节点的自动采用路径中。
3. `validate_prices_step` 只核查已有成本的行，结果存入 `validation_results[item.item_id]`。范围或历史偏差的警告写入报价项备注；现有规则仍没有把这些警告变成强制审批。该节点完成历史价格查询后才保存首次任务快照；若读取历史价格失败，本轮不会留下“查价中”的半成品。
4. `human_review_decision` 看到待处理行就进入 `human_review_step`；后者显式将状态设为“人工确认”。`build_agent` 的 `human_review → END` 表示本次图执行结束，并非 LangGraph 持久化中断。
5. `apply_manual_prices` 要求任务仍在人工确认状态、所有待处理行均有合法施耐德品牌和型号，并且请求里的 ID 集合与待处理 ID 集合完全相同。它先计算全部替换项，再统一写回；少提交、重复提交或低到舍入后单价为零的价格会报错。这里的“人工录价”只形成**待审批草稿**，不表示采购价已被企业批准。
6. `calculate_step` 拒绝仍有待处理行的任务，用 `Decimal` 对行价求和，并把任务设为“完成”。这里的“完成”指草稿计算完成，不是客户版本发布。状态写入 `quotation_tasks`；`get_task_state` 从数据库恢复。

## 必须掌握的 Python 基础

必须掌握：`TypedDict`、`dict` 按键取值、集合相等比较、列表推导、函数返回值、`None`、异常。可以暂缓：LangGraph 并行 reducer、内置检查点、分布式任务队列。

## 常见错误与排查

- 任务 404：先检查任务 ID 与数据库路径；旧内存版中未保存的任务无法自动迁移。
- 补价返回 422：检查 `pending_products[].item_id`，是否一次提交全部 ID；品牌或型号问题需修正 Excel 后重传。
- 两行同名产品：检查 `item_id` 和 `validation_results` 是否按行区分，不能按名称提交价格。
- 查到网页价格仍待处理：主工作流不自动采用未核验的网页候选价。
- 上传返回 503：表示本地价格库读取/解码失败，暂时不能继续；它与健康查询返回空列表不同。接口清理本次上传，不创建任务或事件。

## 技术面试可能问

**这是自主 Agent 吗？** 当前节点顺序和分支由代码决定，是确定性工作流。**人工确认能跨重启恢复吗？** 可以，任务由应用层保存到 SQLite；这不是 LangGraph 自带检查点。**为什么要先完整校验再写回？** 避免一部分行已改价、另一部分失败，留下不一致的报价草稿。
