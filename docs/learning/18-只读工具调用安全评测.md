# 18 只读工具调用的后端安全边界评测

## 业务目标：分别验证模型和后端

只读助手有两类风险：模型可能选错工具；即使模型提出危险调用，后端也必须拒绝。前者要通过真实模型和有标注的问题评估，后者可以先用固定的合成调用直接验证后端白名单。本教程只覆盖第二类。

app.tool_call_evaluation 调用 app.assistant._run_tool()，检查允许的只读工具是否能返回预期结果，以及未知写工具、额外参数、畸形 JSON、超长查询和缺失调用 ID 是否被拒绝。它不请求模型、不读数据库、不运行审批/补价/导出写操作。通过结果不是完整安全验收。

## 评测数据与结果

固定案例位于 tests/fixtures/synthetic_tool_call_eval.json，包含 5 个允许案例和 5 个拒绝案例。每个案例标注 expected_outcome；成功读取产品的案例还核对来源 ID。任务状态工具使用合成上下文，另有无上下文案例，确认它返回“未关联任务”的安全信息。

报告按案例列出预期与实际的 allow/deny、来源 ID、是否匹配。汇总 exact_case_rate 是这 10 个合成调用案例的通过比例，不可称作模型工具调用准确率、漏洞率或企业安全指标。

## 核心代码路径

1. load_dataset() 只接受 data_class=synthetic 的数据集，并检查案例结构和唯一 ID。
2. _evaluate() 为普通案例构造固定的合成任务上下文；数据集中显式写 context=null 时，模拟无关联任务。
3. 每个案例交给 _run_tool()。它要求 call ID、JSON 参数、工具名和参数键符合服务端白名单。评测只把 AIRequestError 记为预期拒绝；意外异常会直接暴露为评测错误。
4. 对允许调用，评测比较来源 ID 和可选的响应内容片段。这样可以发现“放行了但返回错了资料”的问题。
5. main() 以 JSON 输出可复核逐例报告。

## 运行方式

```bash
.venv/bin/python -m app.tool_call_evaluation
.venv/bin/python -m pytest -q -p no:cacheprovider tests/test_tool_call_evaluation.py
```

评测不会连接 Responses API。即便十个案例全部通过，也只说明 _run_tool() 在固定合成输入下满足期望，不证明 API 认证、真实数据库权限、模型行为或未知攻击输入都正确。

## 如何扩成真实模型评测

取得授权后，冻结一组中文问题和人工标注的预期工具/参数/预期拒答，记录模型名称、版本、提示词版本和工具 schema 版本。把“模型请求是否正确”与“后端是否安全执行”分开计算；对每个错误保留原始问题的脱敏 ID、工具名、参数错误类别和人工裁定。真实任务摘要和客户数据在确认外发政策前，不应送往外部模型。

至少分开报告：工具选择准确率、参数有效率、该拒绝时的拒绝率、允许调用的结果正确率、引用来源覆盖率。还需测试 API 级身份与任务归属；本评测器绕过了 API 认证，不能替代这类测试。

## 面试可能问

**十条测试全过能说明 Agent 安全吗？** 不能。它仅覆盖固定后端分派案例，真实模型是否正确调用工具、接口身份权限和企业数据策略都未评估。

**为什么同时测试 unknown write tool 和多余 task_id？** 前者验证没有白名单的写工具不能被模型名称动态调用；后者验证模型不能用参数覆盖应用绑定的任务上下文。

**怎么评估真实模型的 tool calling？** 冻结有许可的问题，人工标注预期工具、参数和应拒答案例，固定模型/提示/schema 版本，逐例比较模型请求与预期，再独立确认后端工具结果和权限边界。

## 小练习

1. 在合成 fixture 中新增 get_product_details 携带 task_id 的拒绝案例，运行 CLI 并检查该例的实际结果。
2. 把 approve_quote 错误地设成 expected allow，观察报告如何区分行为结果与期望标签；随后恢复安全的 deny 标签。
