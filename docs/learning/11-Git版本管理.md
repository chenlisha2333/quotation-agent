# 模块 11：用 Git 管理报价 Agent 版本

更新日期：2026-10-21。本项目的 Git 仓库在本次检查前已有 `main` 分支，但没有提交历史，也没有远程仓库。因此这次建立的提交只能称为**当前项目基线**，不能假装还原出以前每轮开发的独立提交。

## 1. 模块的业务目标

报价规则、产品匹配和导出模板可能随业务确认而变化。版本管理要回答：“某份报价草稿是按哪一版代码生成的？这次改动改了哪些文件？若新改动有问题，能否回到已验证的版本？”Git 保存代码和教学文档的变化；具体报价任务的成本与审批记录仍由 SQLite 保存，两者用途不同。

## 2. 核心技术及其作用

- **仓库（repository）**：简单说是保存项目版本的目录；专业定义是带 `.git` 元数据的文件树。本项目仓库根目录包含 `app/`、`tests/`、`templates/`、`docs/learning/`。
- **提交（commit）**：简单说是给一组已检查的文件拍一张有说明的快照；专业定义是指向文件树及父提交的不可变对象。以后每个功能模块形成自己的提交。
- **分支（branch）**：一条可前进的开发线。当前主分支叫 `main`；较大的新功能可以先建功能分支，测试后再合入。
- **标签（tag）**：给某个提交一个稳定名字。本次基线标签仅表示本机已验证原型，不表示企业生产发布。
- **忽略规则（`.gitignore`）**：告诉 Git 不要纳入本机文件。本项目已忽略 `.env`、`.venv/`、`data/`、数据库、日志和运行输出。

## 3. 为什么选择这种方案

项目已经有 Git 仓库和忽略规则，直接建立基线即可，不需要引入额外版本服务。当前没有远程地址，所以提交和标签暂时只保存在这台电脑；本地提交不是异地备份。真实客户询价、供应商成本和密钥不能因为“需要可追溯”就提交到仓库，业务数据的留存与访问控制应单独设计。

## 4. 与其他模块的关系和数据流

```text
修改 app/、templates/ 或 tests/
  → 运行相关测试
  → 更新 docs/learning/教程与学习进度
  → 查看 git status / diff
  → 只暂存本模块文件
  → 检查暂存清单
  → git commit
```

代码版本通过 Git 追溯；报价任务通过 `app/db.py` 的 SQLite 快照和事件追溯；每一行金额还保存 `pricing_rule_id`。这三层分别回答“哪版程序”“哪次业务操作”“哪版计价规则”。

## 5. 相关文件路径和关键函数

| 文件/位置 | 用途 |
|---|---|
| `.gitignore` | 排除本地密钥、数据库、虚拟环境、缓存和输出 |
| `app/config.py::PRICING_RULE_ID` | 标识当前草稿公式，不能只靠 Git 提交号代替业务规则版本 |
| `app/pricing.py::calculate_item_price` | 在 `QuotationItem` 中写入实际使用的规则 ID |
| `app/db.py::save_task_snapshot` | 保存某次报价任务状态；它不是 Git 提交 |
| `tests/` | 在每次提交前验证行为 |
| `docs/learning/学习进度.md` | 记录模块、教程、测试和待解决疑问 |

## 6. 核心配置与命令逐段解释

`.gitignore` 的 `.env` 和 `.env.*` 规则避免把本地密钥写进版本库；`!.env.example` 允许提交**没有真实密钥的示例配置**。`/data/` 排除报价数据库和上传文件。`templates/施耐德询价表示例.xlsx` 是无真实成本的教学/询价模板，可以纳入版本库；其中“供应商报价回填”单价为空。

在项目目录执行 `git status --short`，先看工作区有哪些变化。`git add <本模块文件>` 把要提交的文件放入暂存区；暂存区像提交前的购物篮。`git diff --cached --stat` 核对清单，`git diff --cached` 核对文本变化，再执行 `git commit -m "feat: 简短说明"`。`git log --oneline -5` 看最近提交。提交后再执行 `git status --short`，确认没有漏掉或误纳入的文件。

已有提交若出现问题，先用 `git show <提交号>` 查明改动。需要撤销已公开的提交时，优先与团队确认后用 `git revert <提交号>` 产生新的反向提交；初学阶段不要对有业务资料或团队共享的仓库直接使用 `git reset --hard`。

## 7. 必须掌握的基础知识

**必须掌握**：文件路径、工作区/暂存区/提交三种状态、`git status`、`git add`、`git diff --cached`、`git commit`、`git log`、`.gitignore`。可把它们理解为“正在编辑 → 选中要保存的文件 → 保存一版”。

**暂时可以跳过**：交互式 rebase、cherry-pick、签名提交、复杂分支策略和自动发布流水线。等有远程仓库和多人协作后再引入。

## 8. 实际运行与验证方法

在项目根目录运行：

```bash
.venv/bin/python -m pytest -q -p no:cacheprovider
git status --short
git log --oneline -3
git check-ignore -v .env data/quotation.db .venv/bin/python
```

基线建立前完整测试为 **35 passed**。`git check-ignore` 应指出本地配置、数据库和虚拟环境的忽略规则；不会显示示例询价模板，因为该文件需要纳入版本管理。后续每个模块在测试通过、教程同步后再提交。

## 9. 常见错误和排查

- **`git status` 显示所有文件都是 `??`**：这是本项目在初始提交前的真实状态；基线提交完成后再运行应为空。
- **提交里出现 `.env` 或 `data/quotation.db`**：先停止提交，检查 `.gitignore` 和 `git diff --cached --name-only`。若文件以前已被追踪，仅写忽略规则不会自动移除追踪。
- **找不到旧版功能的单独提交**：项目此前没有提交历史，无法凭空恢复；基线之后才有可比较的增量。
- **另一台电脑看不到提交**：当前没有配置远程仓库，必须由项目所有者决定是否创建私有远程并处理客户数据与访问权限。

## 10. 技术面试可能问的问题

1. **为什么 `.gitignore` 不能保护已经提交的密钥？** 它只影响尚未追踪的文件；已提交的内容还留在历史中，需要撤换密钥并按团队流程处理历史。
2. **为什么计价规则 ID 和 Git 提交号都要保留？** Git 号标识代码快照；规则 ID 表达报价适用的业务算法版本。一个代码提交可能同时包含多个算法或非计价修改。
3. **为什么本地提交不是备份？** `.git` 仍在同一台电脑上；磁盘丢失会一起丢失。要经许可配置私有远程或备份。
