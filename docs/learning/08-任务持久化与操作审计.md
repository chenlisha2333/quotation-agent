# 模块 4：任务持久化与操作审计

更新日期：2026-10-21。本模块把报价任务从进程内字典迁到 SQLite。它解决“页面刷新、服务重启后任务消失”和“重复人工补价产生不同结果”这两个原型问题。当前审计事件记录**操作类型和数据**，但没有操作者身份验证；它还不是正式企业审批审计。

## 1. 业务目标：为什么先保存任务

报价员上传 Excel 后，可能隔天才补成本价。如果任务只放在 Python 内存里，服务重启就要重传文件、重新核对价格。现在每次工作流到关键步骤时，任务及其明细写入 `data/quotation.db`。`GET /tasks/{task_id}` 和补价接口都从数据库读取，所以重启后可继续。人工补价成功时，状态和一条“人工补价并完成草稿”事件同时提交；重复提交相同价格返回原结果。

## 2. 核心技术及作用

- **SQLite**：简单理解是保存在一个本地文件中的数据库。专业定义是支持事务的嵌入式关系数据库。这里适合单机原型；多人部署还需进一步评估。
- **Pydantic 模型**：在 `TaskSnapshot` 中明确持久化字段，并将 `Decimal`、`Product`、`QuotationItem` 转成 JSON，再在读取时校验和恢复。简单理解是“存盘前后检查数据结构”；专业定义是运行时数据验证和序列化。
- **事务**：简单理解是“状态和事件一起成功或一起失败”。`save_task_snapshot` 在一次 SQLite 事务中更新任务并写事件。
- **乐观并发版本**：简单理解是“修改前看一眼是不是自己读过的那一版”。每次保存必须带 `revision`；数据库版本若已变化，会抛出 `TaskConflictError`，避免旧状态覆盖新状态。

## 3. 为什么这样实现

仓库原来已经有 `quotation_tasks` 表，但没有使用。增量增加 `version` 列和 `task_events` 表，比引入新数据库更符合当前单机结构。`TaskSnapshot` 保存业务状态，不直接把 Python 对象交给 `json.dumps`，因为原生 JSON 不认识 `Decimal` 和 Pydantic 对象。价格仍以十进制字符串往返，读取后恢复为 `Decimal`，金额精度不会被数据库 JSON 浮点数破坏。

本模块的补价事件不记录实名操作者；后续[角色审批模块](09-角色审批与客户报价.md)增加本机令牌对应的审批人名称，但仍未接入企业身份系统，不能当作不可抵赖的实名签核。当前 `完成` 仅表示内部草稿计算完成。

## 4. 与其他模块的关系和数据流

```text
Excel → parser.py → Product → agent.py 的 LangGraph
                                  ↓ 关键节点保存
                            db.py / quotation_tasks + task_events
                                  ↑ 读取并恢复
页面 → main.py 的 GET /tasks/{id}、POST /tasks/{id}/confirm
                                  ↓
                             定价与内部草稿导出
```

`price_lookup_step`、`validate_prices_step`、`human_review_step` 和 `calculate_step` 保存状态。`apply_manual_prices` 先完整校验所有待补价行，再一次保存最终草稿。旧价格记录仍在 `price_records`；任务快照并不更改价格库。

## 6. 核心代码逐段解释

先看 `app/agent.py` 的 `TaskSnapshot`：它列出任务 ID、人民币、产品、报价项、待处理行、消息、验证结果和 `revision`。`save_task_state` 调用 `snapshot.model_dump(mode="json")`，让金额成为字符串，随后调用数据库函数。`get_task_state` 用 `TaskSnapshot.model_validate(payload)` 把字符串金额恢复为 `Decimal`，把嵌套字典恢复为 `Product` 等模型。返回 `snapshot.__dict__.copy()` 是为了保留这些模型对象；普通 `model_dump()` 会再次把嵌套对象变成字典。

再看 `app/db.py` 的 `save_task_snapshot`：`BEGIN IMMEDIATE` 开始写事务；读取当前版本，与传入的 `expected_version` 比较。不一致就抛 `TaskConflictError`，整个事务回滚。一致则更新 `quotation_tasks`，在同一事务插入 `task_events`，最后提交。事件采用 `(task_id, version)` 唯一约束，便于按顺序追查。

最后看 `apply_manual_prices`：它先重新从数据库读取任务。如果已经 `完成` 且人工价格与请求相同，就直接返回；若价格改变，则拒绝在旧任务上偷偷改价。仍在 `人工确认` 时，先检查产品品牌、型号、全部明细 ID 和金额，算好所有替换项后，才保存一次最终状态。并发中如另一请求抢先保存，数据库版本检查会阻止覆盖；HTTP 接口返回 409，客户端需重新读取。

## 7. 必须掌握的 Python 基础

**必须掌握**：`dict` 的键和值、函数参数和返回值、`try/except/finally`、`Decimal("12.34")`、Pydantic 模型与普通字典的区别、`None` 的含义。特别注意 `Decimal("10") == Decimal("10.00")`，所以重复请求中这两种写法被视为同一价格。

**可以暂缓**：数据库隔离级别细节、分布式锁、多节点数据库迁移。当前代码只保证 SQLite 文件上的版本比较；不宣称已解决正式多用户权限问题。

## 9. 常见错误与排查

| 现象 | 可能原因与处理 |
|---|---|
| 404 任务不存在 | 任务 ID 错误、旧版本仅存在内存、数据库路径换了；检查 `app/config.py` 的 `DATA_DIR`。旧进程内存任务无法在升级后补救。 |
| 409 任务已更新 | 两个操作读到同一旧版本；刷新任务，确认新状态后再决定是否提交。 |
| 422 必须一次提交全部行 | 对照 `pending_products` 的 `item_id`，不能按产品名称补价。 |
| 数据库写入失败 | 检查 `data/` 写权限和磁盘空间。保存失败时接口不应声称补价成功。 |
| 读取金额变成字典或字符串 | 检查是否通过 `TaskSnapshot.model_validate` 恢复，勿直接使用原始 JSON。 |

## 10. 技术面试可能问什么

1. **为什么要同时保存任务状态和事件？** 状态便于快速恢复当前草稿；事件解释关键状态怎样产生。二者同事务保存，避免“状态变了但无事件”。当前事件无实名身份，不能当正式审批证据。
2. **如何防止重复补价？** 相同已完成请求直接返回原任务；不同价格必须开新修订流程，当前还未实现；并发旧版本由数据库 `version` 拦截。
3. **为什么不直接使用 LangGraph 内存状态？** 内存随进程结束而消失；数据库快照使 HTTP 请求之间和重启后能恢复。这里是应用层快照，不是 LangGraph 自带 checkpoint。
