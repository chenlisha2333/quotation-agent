# 模块 3：人民币与施耐德产品匹配

更新日期：2026-10-21。本模块落实已确认的两条项目约束：**报价币种为人民币 CNY；清单中的电气产品按施耐德品牌处理**。目前对上传清单的每一行执行品牌约束，包括柜体、线缆和辅材；若某类产品以后允许例外，需要先明确业务规则再修改代码。

## 业务目标：为什么要先核对品牌和价格

原型按产品名称或型号模糊查价，可能把“正泰断路器”与其他型号的价格用于施耐德报价。即使金额算得完全准确，选错产品也会使报价失真。本模块让每行先拥有独立的明细 ID，再核对品牌、型号、规格、单位、人民币币种、价格来源、有效期及人工核准标记。信息不足时停在待处理状态，不编造施耐德型号或成本。

**简单理解**：“施耐德”是品牌要求，“A1/32A/个”是要买的具体产品，“CNY 12.34”是某份报价单上的价格；三者必须指向同一件东西。**专业定义**：这是以产品属性和价格元数据为条件的确定性匹配与准入校验。当前 `verified` 只是价格记录上的标记，尚未实现企业角色审批，不能当作正式采购批准。

## 核心技术、作用和方案选择

| 技术 | 在本模块的作用 | 为什么这样实现 |
|---|---|---|
| Pydantic | `Product.item_id`、`PriceRecord` 的品牌/币种/来源/有效期、`QuotationItem.currency` | 给 API、工作流和数据库同一份字段定义；旧价格的币种留空，不假定它是人民币 |
| SQLite | 保存 `brand`、`spec`、`unit`、`currency`、`source_reference`、`valid_until`、`verified` | 沿用现有本地库，增列兼容历史文件，不引入新数据库 |
| LangGraph | 查价、人工处理和计算之间的条件分支 | 保留原有工作流结构，只收紧进入“可报价”的条件 |
| 明细 ID | `line-1`、`line-2` 等区分一次任务中的每一行 | 两行产品名称相同也不会共用人工价格或核查结果 |
| FastAPI 与页面 | 返回待处理原因，按明细 ID 一次提交全部人工成本价，按任务 ID 导出 | 服务端从任务状态取导出内容，减少页面修改报价明细造成的不一致 |

没有引入自动品牌替代模型，也没有给现有样例制造施耐德价格。可自动采用的本地价格条件较严格；缺少正式价格数据时，进入人工处理是预期行为。网页抓价代码仍保留为实验适配器，但**不再进入自动报价主流程**。

## 与其他模块的关系和数据流

`Excel → app/parser.py::parse_excel → Product → app/agent.py::init_state 分配 item_id → app/product_policy.py::product_issue → app/db.py::search_local_price → eligible_price → app/pricing.py::calculate_item_price → 价格核查 → 报价草稿`。

如果品牌或型号不合要求：`pending_products + review_reasons → API 与页面展示 → 修改 Excel 并重新上传`。如果品牌型号符合但缺少合格价格：`按 item_id 人工录入全部成本价 → apply_manual_prices → 重新计算 → 完成草稿`。导出时：`页面发送 task_id → app/main.py 从服务端任务取明细 → app/exporter.py 输出人民币内部草稿`。

## 真实代码逐段解释

1. **`app/config.py` 与 `app/models.py`**：`QUOTE_CURRENCY = "CNY"`、`REQUIRED_BRAND = "施耐德"` 明确项目约束；`Product.item_id` 保存任务内行标识。`PriceRecord.currency` 可为 `CNY` 或空，空值是旧记录币种未知，自动匹配时拒绝。`QuotationItem.currency` 固定为 `CNY`，API 和内部依据页都能显示币种。
2. **`app/product_policy.py::normalized_brand` 与 `product_issue`**：把“Schneider”“Schneider Electric”“施耐德电气”归一为“施耐德”；其他品牌仍保留原文。`product_issue` 对非施耐德品牌和缺失型号返回需要修正的原因。它不把原来的正泰、德力西型号自动改写成施耐德型号。
3. **`app/product_policy.py::eligible_price`**：先检查产品是否满足品牌与型号要求，再检查价格记录的币种、核准标记、来源凭证、有效日期、`decimal_text` 精度以及名称、型号、规格、单位是否逐项一致。任何一项不满足就返回 `False`。`app/db.py::search_local_price` 先按名称和人民币筛选，再调用此函数；旧库 `REAL` 价格、无来源凭证或过期记录不会被自动采用。
4. **`app/agent.py::init_state` 与 `price_lookup_step`**：给上传清单的每一行分配 `line-1`、`line-2` 等 ID。查价节点先运行 `product_issue`；通过后才查严格匹配的本地价格。符合条件的价格进入金额计算，其他行写入 `review_reasons[item_id]` 并等待处理。`validation_results` 也改按 ID 记录，重名不会覆盖。
5. **`app/agent.py::apply_manual_prices`**：要求任务处于“人工确认”；品牌或型号有问题时拒绝成本价提交，提示重新上传。可补价的任务必须一次提供全部待处理 ID，不能靠只补一部分就变成“完成”。先逐项计算和检查，再一次替换任务明细；失败时原明细不被部分修改。重复确认已完成任务会报错。
6. **`app/main.py::_task_response`、`confirm_prices`、`export_quotation_endpoint`**：接口返回 `currency`、`item_id`、待处理原因和 `can_enter_price`。人工补价 JSON 格式为 `{"line-1": "12.34"}`。导出请求现在只发 `{"task_id": "..."}`；后端核实任务状态、品牌、成本和币种后，从自己的任务状态导出，而不是信任浏览器回传的明细。
7. **`static/index.html` 和 `app/exporter.py`**：页面显示人民币、品牌与明细 ID。品牌或型号问题时禁用补价按钮，要求修正 Excel；待处理时禁用导出。Excel 标题标明“人民币 CNY，内部草稿”，计算依据页也保存 `CNY`。页面中的产品文字经过 HTML 转义，避免上传文件中的特殊字符被当作页面代码执行。

## 常见错误与排查

- **所有样例行都待处理**：样例中大部分是其他品牌，唯一标为施耐德的行也没有经核准的匹配价格。这是本轮规则的预期结果。
- **输入价格仍无法确认**：查看 `pending_products[].reason`。品牌或型号问题需修改上传表；只有明确为施耐德且有型号的行可以人工补价。
- **同名两行价格串了**：检查请求是否使用 `line-1`、`line-2`，不要再按产品名称发送价格。
- **数据库里明明有价却不命中**：逐项核对品牌、型号、规格、单位、CNY、`verified`、来源凭证和 `valid_until`；旧 `REAL` 价不会自动采用。
- **导出返回 404/409**：404 表示任务 ID 不存在；409 表示任务尚未完成、含不合格明细，或客户版本尚未发布。任务现存于 SQLite；审批见[模块 5](09-角色审批与客户报价.md)。

## 技术面试可能问

**为什么不把正泰型号替换为“相近”的施耐德型号？** 型号替代涉及电气参数、安全及采购确认；当前系统没有经过核验的替代关系，自动改写会掩盖风险。

**为什么有 `verified=True` 还不能说已完成审批？** 目前它只是单条价格记录的技术准入标记，没有操作者身份、审批权限、原因和不可变审计记录。正式审批流程仍需开发。

**为什么导出要按任务 ID？** 后端可使用持久化任务的明细和客户信息，避免浏览器提交一份与任务结果不一致的价格表。客户版另外从冻结版本读取。
